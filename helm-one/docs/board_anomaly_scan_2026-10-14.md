### 建议上板测试顺序

1. **正常骑行保存**：录制、暂停、继续、结束保存，再开启下一趟；确认 GPX 可打开且没有重复轨迹点/结束标签。

3. **BLE 列表**：常规目录正常列出；MTU 23 或超长名称时返回错误而非一直转圈；断开重连后可继续操作。
4. **BLE 上传与覆盖**：上传 GPX/图标并覆盖同名文件，成功通知到达后立即读取校验。无效图标应报失败，旧图标仍存在。大文件末尾需等待真实落盘。
5. **保存故障恢复**：在测试介质上模拟满盘或 I/O 错误；界面给出保存失败提示，操作保持可用。恢复存储后等待后台重试，确认 GPX 最终完整，并可开始下一趟。

7. **中断提交**：在测试介质验证覆盖期间断电，检查正式文件、`.part`、`.bak`；保留恢复副本，不在唯一重要文件上做此测试。

### 需了解的边界

- 当前 NuttX VFS 的 rename 会先 unlink 已存在的目标，故采用 `.bak` 保护，而非声称覆盖 rename 本身具有原子性。掉电/回滚失败可能留下 `.bak`；设备拒绝覆盖该备份，可通过文件传输将它改回正式名或确认内容后删除，再重试上传。尚未实现开机自动恢复所有备份。
- 关闭的 10 秒限制约束调用方等待，有限重试约束应用层循环；无法强行打断底层驱动单次阻塞系统调用，驱动时序需上板验证。
- GPX 待写缓存保留在 RAM，掉电仍会丢失尚未落盘的部分；已落盘文件和恢复标记会保留，不能把本修复理解为掉电零丢点。
- 普通上传最终成功现在晚于此前版本。手机端源代码不在本轮范围内；若手机 CLOSE 等待超时短于实际存储耗时，需配合延长等待。固件不会再为规避超时而提前报成功。
- 主机测试不模拟实际 LittleFS、BLE 链路或驱动，只验证函数逻辑；上述上板项目仍需实际确认。

## A01：文件提交失败可能同时失去旧文件和临时文件

位置：[transfer_backend.c](../boards/sf32lb52/helmone/services/transfer_backend/transfer_backend.c)，`xfer_write_commit()`，908–933 行。

- 当前顺序为 `close(fd)` → `unlink(final_path)` → `rename(tmp_path, final_path)`。
- 如果 rename 失败，又调用 `unlink(tmp_path)`；旧文件已被删除，新文件也无法用于恢复。即使 rename 成功，删除与改名之间断电也存在正式文件缺失的窗口。
- `close()` 的错误被忽略，后续仍可能提交并返回成功；错误分支在清理临时文件后才取 errno，也可能覆盖最初的 rename 错误。
- 触发：覆盖已有文件时临时文件不存在，或 rename 因存储 I/O 等原因失败。BLE 普通文件和 OTA 都调用此函数，参见 `companion_fs.c:865,1390`。

主机复现：先建立含旧内容的正式文件，传入不存在的 `.part` 路径，执行原函数。结果：

```text
commit_missing_part: errno=2 old_exists=0
```

建议：检查关闭/同步结果；优先使用底层文件系统支持的覆盖式 rename，并确认其原子性。若不支持，设计备份与恢复流程。提交失败保留可恢复数据，并在清理前保存错误码。

验收：注入 close/rename 失败及提交中断电，旧正式文件或完整新文件至少保留一份，调用方收到失败。

## A02：BLE 列表遇到单页装不下的文件名会停住

位置：[transfer_backend.c](../boards/sf32lb52/helmone/services/transfer_backend/transfer_backend.c)，`xfer_list_pack()`，527–630 行；[companion_fs.c](../boards/sf32lb52/helmone/services/ble_companion/companion_fs.c)，`payload_budget()` 651 行、`fill_list_page()` 1709 行附近。

每个目录项需要 `10 + 文件名字节数`。如果当前首项超过 `out_max`，函数跳到 `done`，返回 0 字节、`last=false`，游标也不变。下一次请求仍遇到同一项。调用方没有将这个组合转换成错误或推进逻辑，事务无法自行结束。

MTU 为 23 时，预算为 `23 - 3 - 8 = 12` 字节，因此文件名超过 2 字节即可触发。即使协商到更大 MTU，也仍需处理文件名超过预算的情况；中文文件名按 UTF-8 字节数计。

主机复现：目录中放入 `longfilename.gpx`，连续三次调用原函数，预算 12 字节：

```text
list_page0: bytes=0 cursor=0 last=0
list_page1: bytes=0 cursor=0 last=0
list_page2: bytes=0 cursor=0 last=0
```

建议：当单条记录无法放入空页时返回明确错误，或实现协议级分片；若依赖最低 MTU，应在开始 LIST 前明确校验并返回错误，不能空转。

验收：默认 MTU、协商失败、长英文/中文文件名都能成功列出或返回明确错误，不保持无进展会话。

## A03：延迟落盘失败路径泄漏文件描述符

位置：[companion_fs.c](../boards/sf32lb52/helmone/services/ble_companion/companion_fs.c)，`wbuf_flush_chunk()` 383 行、`wbuf_flush()` 449 行、`fs_deferred_commit()` 854–883 行。

`wbuf_flush()` 失败时不会关闭 `g_fs.wfd`；`fs_deferred_commit()` 仅在刷新成功后才调用会关闭 fd 的 `xfer_write_commit()`，但无论成功失败都立即将 `g_fs.wfd` 设为 -1。于是写盘失败后句柄仍打开，而状态已丢失该句柄。

触发：非 OTA 文件在 CLOSE 后的延迟刷新阶段遇到 ENOSPC/EIO。反复失败会累积描述符，并可能使后续 open 返回 EMFILE。这是独立于“提前回复成功”的资源清理问题。

建议：在 flush 失败分支显式关闭或 suspend 原 fd，保留 `.part` 供恢复；明确各函数的 fd 所有权和关闭责任。

验收：重复注入刷新失败，打开文件数保持稳定，后续上传仍可正常创建文件。

## A04：GPX 存储错误无限重试，关闭无法完成

位置：[gpx_port.c](../boards/sf32lb52/helmone/domain/gpx/gpx_port.c)，`gpx_port_file_flush_wait()` 479 行、`gpx_port_file_commit()` 547 行、`gpx_port_file_close()` 767 行；[gpx_record.c](../boards/sf32lb52/helmone/domain/gpx/gpx_record.c)，`gpx_record_close_session_locked()` 448 行、`gpx_record_wait_close()` 1177 行。

- `flush_wait()` 对所有写入错误永久重试；commit 的 wait 模式对 open/fsync 错误也没有截止条件。
- `file_close()` 使用 wait 模式；持续 ENOSPC、EIO 等错误没有不可恢复分支或取消出口。
- 重试循环不断调用 `myvendor_watchdog_hw_pet()`，因此不能指望硬件看门狗自动结束该等待。
- 录制停止通过工作线程关闭文件，`stop_drain` 在关闭后才清理；`wait_close()` 也没有超时。

影响：存储故障持续存在时，录制器可能一直处于关闭状态。UI 关闭轮询 `bicycle_ride_gpx.c:826` 会持续等待。这里**不认定整个 UI 必然卡死**：关闭阶段已经释放录制锁，具体界面和后续录制行为需上板验证。

建议：区分可重试错误与持续错误，设置重试时间上限或可取消状态，向 UI 暴露保存失败；保留可恢复缓存/临时文件，避免直接丢弃骑行数据。

验收：满盘、拔卡、持续 fsync 错误时，可在有界时间进入明确错误状态，并支持恢复或退出。

## A05：目录项跳过后分页游标与扫描位置不一致

位置：[transfer_backend.c](../boards/sf32lb52/helmone/services/transfer_backend/transfer_backend.c)，`xfer_list_pack()`，562–624 行附近。

恢复分页时，`skip` 对每个非隐藏目录项递减；但页尾只按成功打包数 `packed` 增加游标。路径拼接超长或 stat 失败的目录项被 `continue` 跳过，却未计入游标。因此两边对游标含义的定义不一致。

示例（目录顺序稳定）：A 的 stat 失败，B 成功打包，C 使当前页放不下。游标仅加 1；下一页跳过 A 后又打包 B，导致重复。异常项更多时可能持续重复相同页面。

触发：分页目录包含完整路径超过 `XFER_PATH_MAX=256` 的项，或扫描期间 stat 失败的项。普通无异常项的目录不受该分支影响。

建议：统一游标为实际消费的非隐藏目录项数；“已跳过异常项”和“因本页放不下留到下一页的项”分开处理。若需要支持并发目录变动，另行设计稳定分页语义。

验收：注入中间项 stat 失败、完整路径超长，所有有效项最多返回一次，列表最终正常结束。

## R01：普通上传的成功回复不代表已成功落盘

位置：[companion_fs.c](../boards/sf32lb52/helmone/services/ble_companion/companion_fs.c)，1407–1414 行、854–883 行。

普通 GPX/图标等在实际刷新和提交前已经回复 WRITE_CLOSE 成功；随后失败只打印 `fs write commit after-ack failed`，没有向手机报告最终失败。OTA 走同步提交分支，不属于此项。

这是代码明确采用的降低手机等待时间的设计，不应简单删掉延迟机制。但磁盘满、断电或 I/O 错误时，手机可能显示完成而设备缺少文件。当前是否通过手机端回查补偿，本轮未查看手机端，需确认。

建议：区分“接收完成”和“持久化完成”，增加最终结果事件或状态查询；保留异步写盘，避免长时间阻塞 BLE 应答。

验收：在 CLOSE 应答后注入写盘失败，手机能够显示最终失败并提供重试入口。
