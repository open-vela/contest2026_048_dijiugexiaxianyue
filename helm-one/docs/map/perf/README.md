## 1. 出发点：一条反直觉的实测

在埋点之前，静态分析给出的候选优化有十来条。埋点后（见
[MEASUREMENTS.md](./MEASUREMENTS.md)）最重要的一条是这个：

**加了脏区（clip）之后，每个瓦片反而贵 2.5~4.5 倍。**

| 路径 | 每瓦片 |
|---|---|
| 全量重画（`clip_n == 0`，不裁） | 20.8 / 20.9 / 24.0 / 27.2 ms |
| scroll 补边（`clip_n > 0`，裁到脏条） | 61.0 / 71.8 / 92.8 / 95.1 / 95.2 ms |

两组样本**完全不重叠**，所以不是"脏边瓦片恰好更密"能解释的。机制在
`vmap_render.c` 里：`cover_span_fp()` 对图元范围内的**每一个**像素都调一次
`put_pixel()` / `blend_pixel()`，而它们在 `clip_n > 0` 时要调
`canvas_in_clip()` 循环最多 8 个矩形；`clip_n == 0` 时它立刻返回。
**裁剪省下的是 PSRAM 存储，付出的却是全量像素都多一次函数调用 + 矩形循环**，
而整棵树编译在 `-O1`，这些 `static` 函数不会被内联。
按 433²≈187k 像素/瓦片折算：不裁约 27 周期/像素，裁了约 119。

这个结论把"先做哪一条"定死了 —— 它同时指向"内联"和"裁剪要提到 span 级"。

## 2. 落地的三项（只动 `vmap_render.c`）

### 2.1 裁剪从逐像素提到按行（+ 内联）

新增 `row_clip_spans()` / `row_span_merge()`：**先按行算出裁剪矩形与跨度的
并集区间**，再只对这些区间落笔。`cover_span_fp()` 与 `blend_span()` 改成走这条；
`canvas_in_clip()` / `put_pixel()` 标 `static inline`（改完后它们只剩零星调用点）。

不变量：**每个像素仍然只写一次**（并集去重，半透明像素不会被混合两次）；
覆盖度仍然逐像素算 —— 它只与 x 和跨度的两个 fp 端点有关，与裁剪无关，
所以像素值不变。

### 2.2 跨度填充改 32 位成对写

新增 `fill_run_u16()`。`blend_span()` / `render_fill_span()` /
`cover_span_fp()` 的"整像素段"都走它。

> **坑（写错过）**：对齐必须按**地址**判，不能按**下标**判 ——
> `vmap_render_scroll()` 会把行指针本身偏移 `dx` 再交给 `render_fill_span()`，
> 指针可能落在奇数元素上。同文件的 `vmap_render_clear()` 早就在做成对写，
> 但它拿到的是行基址，所以没暴露这个问题。

### 2.3 圆盘去掉逐行 `sqrt`

`fill_disc_aa_fp()` 原本每行算一次 `sqrt((double)(outer2 - dy2))` ——
在这颗只有单精度 FPU 的 M33 上是**软双精度 sqrt** 调用。
而行半宽 `dx(y) = floor(sqrt(outer2 - dy²))` 从"离真圆心最近的那一行"
向两侧**单调不增**，所以只有那一行需要一次真 sqrt，其余行各自递减逼近即可。

> **坑（写错过）**：起点必须取 `cy_fp >> 8`（最近的一行），不能取
> `(cy_fp - 128) >> 8`（真圆心下方一行）—— 后者会出现"起点半宽 < 下一行半宽"，
> 单调逼近就会给出**偏小**的宽度。判据是 `|256·y + 128 − cy_fp|` 取最小。

`draw_road_polyline()` 在每个折线顶点都画一个圆盘，这里正是它的热点。

### 2.4 存储试试块写（`stmia`/`ldmia`）—— **已回滚**

**这一条来自实测的反推**：`render_begin` 在 scroll 路径上要 164~197 ms，而
`force_clear` 路径稳定在 44 ms —— 后者几乎只是把 468 KB 画布清零。于是
117k 次 32 位存储 = 44 ms ⇒ **约 90 周期/次存储**。90 个周期付在 4 字节上，
说明时间不在数据上，而在**每次访问**上。

根因：`mpu_config()`（`chips/drivers/cmsis/sf32lb52x/Templates/system_bf0_ap.c`）
把 PSRAM（0x60000000）配成 **write-through**，所以画布的每一次存储都真的打到
PSRAM。

**当时推出的结论**是"PSRAM 挂在 MPI（QSPI 存储控制器）上，每次访问要付命令+地址
开销 ⇒ 按**存储次数**计费"，于是改用固定大小结构体赋值（`vmap_blk32_t`）让 GCC 发
`stmia`/`ldmia`：`fill_run_u16()` / `vmap_render_clear()` / `vmap_render_scroll()`
的行内搬运都走块写（后者还要处理对齐判定与重叠回退）。

**结果：`blk/w = 100%`，推算错了，整批回滚。** 见下面 §2.5。

> **坑（写错过，留着防回归）**：块写要处理**字对齐** —— 多字访问（`ldmia/stmia`）
> 要求字对齐，否则 UsageFault；而且对齐必须按**地址**判而不是下标判
> （`vmap_render_scroll()` 会把行指针本身偏移 `dx` 再交给 `fill_run_u16()`，
> 指针可能落在奇数元素上）。横向平移奇数像素时 dst/src 只差 2 字节偏移、
> 不可能同时字对齐，必须退回 `memmove`。这两处**都是** [verify/harness.c](./verify/harness.c)
> 在开发过程中抓出来的，不是事后想到的。

### 2.5 实测否掉了"访问次数"这个模型

`[vperf] psram` 自检（见 [MEASUREMENTS.md](./MEASUREMENTS.md) §2.5）在同一批
128 KB 上分别做逐字写与块写：

```text
word_w=2909435  blk_w=2929585  word_r=878495  cyc   blk/w=100%
```

| | 周期/字节 |
|---|---|
| 逐字写（4 字节/次） | 22.2 |
| 块写（`stmia`） | 22.4 |
| 逐字读 | 6.7（**下界**：可能部分命中 D-cache） |

**逐字写和块写的周期/字节完全一样** ⇒ 时间花在**字节**上，不在访问次数上，
写通路根本不合并。所以：

- **块写整批回滚**（`vmap_render.c` 相对 `842f55ec` 只剩两处说明注释，非注释代码
  改动 0 行）。它能省指令，但省不了访问。
- **画布专用 write-back region 同样不做**，理由是同一条：字节数一个没少。
- 写速率两次独立吻合：自检 22.4 周期/字节，与"清 468 KB 画布 = 44 ms ⇒
  22.4 周期/字节"一致 ⇒ **≈10.6 MB/s**。

#### 一个连带的重要修正：光栅化是**算力**受限，不是写受限

背景填充走满整张画布，而瓦片是**相邻拼贴**、总共只覆盖画布一次，所以一个全量帧
的写入量 ≈ 画布面积 468 KB + 其上的多边形 ≈ 0.6~0.7 MB，按 22 周期/字节是
**≈17%** 的 `cyc_tile`（实测全量帧 `cyc_tile` = 84M 周期 = 350 ms，其中写入约
60 ms）。

**⇒ 剩下的 83% 是每像素的计算**（覆盖度、混合、光栅化循环）。这条把方向钉死了：

- 第一梯队那三项（内联 / span 级裁剪 / 圆盘去 sqrt）打的正是算力，方向对；
- 下一步该继续压**算力**：§2.3 的多边形每边一次斜率、图元级 bbox 早退、
  以及第二梯队的结构性项；
- 而"减少写入字节数"最多只能拿回那 17%，不是大杠杆 —— 这条我在提"调小
  `VMAP_CANVAS_MARGIN`"时就差点想当然过一次，顺带把它也算否了：每个 rebase 的
  成本 ∝ 画布面积、rebase 次数 ∝ 1/margin，两者相乘后对 margin 几乎不敏感
  （M=128 → 1829，M=96 → 1836）。

> 注意 `word_r` 是**下界**：读可能命中 D-cache。写侧没有这个问题
> （write-through 下缓存不吸收写），所以 22 周期/字节这个数是可靠的。

## 3. 怎么证明"像素逐位不变"

这类改动的最大风险是"快是快了，但画错了一点"。本目录的
[verify/harness.c](./verify/harness.c) 就是为此写的：

- 测试主体**拼在 `vmap_render.c` 之后**编成同一个编译单元 ⇒ 能直接调用它的
  `static` 函数；配 `-ffunction-sections -Wl,--gc-sections` 把不需要的外部符号
  （`vmap_style_current` 等）整段丢掉，**不需要写桩**。
- 两个二进制：**改动前的 `git show HEAD:<file>`** 与**工作区版本**，
  吃同一批随机输入（自研 LCG + 固定种子），比对整块画布的字节。
- 画布宽故意取 **67（奇数）**：专门走成对写的"奇数起点 / 奇数尾"分支。
- 裁剪矩形**有一半概率互相重叠**：专门盯"像素被混合两次"。
- **换 `-O` 级别各跑一遍**（-O0/-O1/-O2）：越界、有符号溢出、别名这类 UB
  在不同优化级别下会露出不同的结果。

实测结果（全部 IDENTICAL，约 **5.2 万个随机用例**）：

```text
O0_AA1 : IDENTICAL  (4000 cases)     O2_AA0 : IDENTICAL  (4000 cases, 非 AA 路径)
O1_AA1 : IDENTICAL  (4000 cases)     O1_big : IDENTICAL  (20000 cases, 另一随机种子)
O2_AA1 : IDENTICAL  (4000 cases)     O2_big : IDENTICAL  (20000 cases, 另一随机种子)
```

复跑方法见 [verify/harness.c](./verify/harness.c) 头部注释。

## 4. 实测收益

同场景硬对比（两场的 `tickd` 都是 221，即同一时刻的同一帧，`tiles=16 warms=14`）：

| 段 | 改前 | 改后 | 变化 |
|---|---|---|---|
| `cyc_tile` | 104,409,593 | 83,984,744 | **−19.6%** |
| 每瓦片 | 6.53 M（27.2 ms） | 5.25 M（21.9 ms） | **−19.6%** |
| `cyc_begin` | 10,555,955 | 10,550,082 | −0.06%（未动，符合预期） |
| `cyc_warm` | 179,664,276 | 180,007,912 | +0.2%（未动，符合预期） |

scroll 补边（形状相同但非同一场景）：`dirty=4 tiles=4` 那一对是
61.0 → **43.7 ms/瓦片（−28.2%）**；按各场均值是 −36% ~ −42%。
补边降幅明显大于全量帧，正符合预期 —— 逐像素裁剪测试本来就是裁剪路径的额外开销。

**裁剪的"倒亏"收窄了但没消失**：每瓦片「裁 / 不裁」的比值从 3.58× 降到 2.21×
（各 4~5 帧均值，内容混合，只作方向参考）。要彻底拉平，得走到图元级 bbox 早退。

**帧时长只小幅改善**，因为光栅化不是帧时长的大头（详见 MEASUREMENTS.md §5）：
全量帧的 `cyc_tot` 几乎没动（被 ~750 ms 的 SD 读盘和 pump 节拍主导），
补边帧则从 764.2 ms 降到 638.7 ms（**−16.4%**）—— 补边帧没有 I/O，
光栅化的收益能直接体现。

完整数据、埋点方法与时钟标定见 [MEASUREMENTS.md](./MEASUREMENTS.md)。

## 4.6 2026-09-25（三）：多边形填充去掉"逐行 64 位软除"

先量后做：给 `vmap_render.c` 加了图元级周期拆分（`[vperf] prim`），
三次实测（全量帧 + 补边帧）显示 **三个图元占 `cyc_tile` 的 60~73%**，
其中多边形约 40~50%，一帧要做 **1.2~2.7 万次逐行软除**
（`x = xi + trunc((y_scan-yi)*dx/dy)` 的 `int64/int64` ⇒ `__aeabi_ldivmod`）。

改法：每条边只在**被激活**时算一次斜率与余数，之后逐行增量推进
（`a += gr; if (a >= M) { a -= M; x += sgn; } x += gm;`）。难点是必须逐位复现
C 的**向零截断**除法 —— 朴素地维护"`|余数| < |dy|`"会让商漂一位（余数的符号
约定也是解的一部分），所以换成全非负的 floor 形式，理由与推导写在
`vmap_render.c` 的注释里。

收益（**定点自测 A/B，同一批确定性多边形，与地图内容无关**）：

| 路径 | 改前 | 改后 | 差 |
|---|---|---|---|
| fp（道路带四边形 + 12 边形） | 9,842,831 | 9,571,632 | −2.8% |
| 整像素（16/64/256 点面要素） | 118,073,558 | 108,680,471 | **−8.0%** |
| 合计 | 127,916,389 | 118,252,103 | **−7.6%** |

折算到整帧约 **−3%（≈7 ms / 235 ms）** —— 比"去掉一次 200 周期的软除"应该拿到的
少得多，原因是**增量推进要把状态写回内存**（每行 2 个字），而 PSRAM 是
write-through（4 字节 store ≈ 88 周期）⇒ 净落只有 12~36 周期/交叉点。
要拿满这块，得让状态留在寄存器里（把循环反过来：外边逐条边走完它的行）或先降
PSRAM 的 store 成本，两条都留作后续。详见
[MEASUREMENTS.md §9](./MEASUREMENTS.md)。

**同时被实测否掉的一条**：状态槽按 `i & 63` 取模复用（省内存）—— 大面要素同时
激活的边多，下标相差 64 的整数倍成对撞同一个槽，每行都要重新装配（两次除法），
`poly` 段 **+13%**，比不改还慢。已回退。

像素不变由 `verify/harness.c` 背书：14 种配置（`-O0/-O1/-O2` × `AA=1/0` ×
两种子 + 高画布）约 30 万例 **IDENTICAL**。

## 6. 2026-09-25（二）：搬运上 DMA（EPIC）—— `cyc_begin` 里那 468 KB 搬走了

出发点就是 §1 那条反直觉实测：使用过程一帧的 `cyc_begin` 里 92% 是
`vmap_render_scroll` 的 468 KB `memmove`（`scr` 字段，122~208 ms）。

- **硬件路径**：EPIC（2D DMA）。基准实测 **EPIC = CPU 的 12% 周期**（同样 186 KB、
  同一矩形）；滚动帧 `scr` 122~208 ms → **两跳 39.8/41.8/45.5 ms、单跳 24.1 ms**，
  帧长降 20~25%（同帧的 `cyc_tile` 不受影响）。
- **两个硬约束**（都靠上板自检实测，不靠假设）：① EPIC 只有"**目的地址低于源**"的
  方向逐位可信，其余方向走**两跳**（src→中转缓冲→dst），没通过自检的方向退回 CPU；
  ② 位移必须落在 `data` 指针上、两层 `x_offset/y_offset` 取同一个值。
- **实现分层**：策略/兜底/自检在 `vmap_blit.c`，芯片那半在
  `services/myvendor_epic_blit.c`（NSH 应用目标看不见芯片层头文件）；
  中转缓冲进程级持有（用户拍板，见 `vmap_blit.c` 的 `s_shared` 注释）。
- 细节、判据表、样本量口径：[MEASUREMENTS.md §8](./MEASUREMENTS.md)；
  **测试怎么做、基线怎么选、缺口在哪**：[TESTS.md](./TESTS.md)；
