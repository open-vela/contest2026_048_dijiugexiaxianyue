# 航向朝上：子矩形旋转（WP-16）—— 已实现、已上板、**已回退**

日期：2026-10-28。结论先行：**方向不成立**，固件已回退；只留下两处独立修复
（EPIC 超时判定、`[epicimg]` 探针清理）。本文记录设计与实测，避免下次重走。

## 1. 想解决什么

航向朝上模式里，正北画布 C（496×472）由 EPIC 旋转进屏幕对齐缓冲 R（288×264）。
整幅旋转实测 **138 ms**（EPIC 任意角 ≈0.551 Mpx/s，线性于输出像素），是当时单笔
最大的 CPU 项（WP-11 §2.2：约 11~17 pp）。

假设：帧外增量（轨迹尾、导航进度灰线）只改 C 的一小块，只把那一块转进 R，
典型 2~9 ms/次，替代整幅。

## 2. 做了什么（已回退，代码见不到，留公式备查）

- 板级原语 `myvendor_epic_rotate_area()`（`services/myvendor_epic_blit.c`）：
  同一变换，只写目的缓冲的一个 clip 矩形。两个关键点当时是**新发现**：
  1. 输出层的 `data` 必须指向 clip 左上角像素（`bf0_hal_epic.h:297-300` 的层约定），
     不是缓冲基址 —— 否则像素会写到缓冲左上角；
  2. 适配层的整层 flush 可以用 `data_size` 掐掉（该字段 HAL 里只有 ezip 分支读），
     自己按反投影出的**源行区间**做 cache clean。
- vmap 侧：C 的脏区 AABB 记账，按**上一次整幅烘焙时**的 `r_pan/r_rot10` 投影到 R，
  只重转那一块；角度变化/余量用完/帧末仍整幅；脏区 > R 面积 3/5 回退整幅。
- 开机自检：整幅留底 → 子矩形覆盖 → clip 内逐像素相同、clip 外不动；失败永久回退。
- 五轮 Codex 只读审查（`gpt-6.1-sol`）把 8 处缺陷逐条改掉后才 ACCEPT。

## 3. 上板实测（固件 build_date 202610282031 / 202610282053 / 202610282102）

板卡：SF32LB52 + NV3031A；`[vrot]` 系列探针，`ctl log all`。

| 负载 | 观察 |
|---|---|
| `demo start linear`（120 km/h 直线） | `[vrot] area` **0 次**；整幅 0.4~0.7 次/s |
| `gnss sim TRK_20260831 fwd 45` | 同上，0 次 |
| `gnss sim TRK_20260831 fwd 8` | 同上，0 次 |
| 导航（`nav …`） | `stamp_nav_then_track` 重描整条路线+轨迹 ⇒ 整幅 |

整幅重烘的触发原因（临时探针 `[vrot] why <c>`，一次 demo 50 s）：

| 原因 | 次数 | 含义 |
|---|---:|---|
| `T` | 17 | 跟车余量用完 / 角度不一致（R 只有 24 px 余量，120 km/h 下 1.6 s 用完） |
| `E` | 6 | 帧末整幅（rebase/换层级） |
| `A` | 1 | 角度待应用（限频 1200 ms） |
| `F`/`N` | 0 | 整画布重描 / 有 pending 无脏区 |

服务侧计数（`[vrot] svc`，2 s 窗口，demo 期）：`svc≈10`（5 Hz）、`blk=0~3`、
`area=0`、`rej=0`、`inv=0~2`。

## 4. 为什么一次都不命中（钉死的证据）

1. **帧外失效本身就是大块**：`[vrot] inv 379,308..813,742` 这类 434 px 见方的矩形
   是 rebase 的瓦片边条，四块一合并就是整画布 ⇒ 子矩形按阈值直接回退整幅（正确）。
2. **导航每 500 ms 重描整条路线 + 整条轨迹**（`stamp_overlays` 用整画布 clip），
   脏区天然是全屏。
3. **不加导航时，帧外几乎没有 C 变更**：不录轨迹时地图内容只在瓦片泵里变
   （帧内），帧末整幅顺手覆盖。
4. **120 km/h 下余量 1.6 s 就耗尽** ⇒ `T` 主导，这一项与脏区大小无关。

也就是说：WP-15 的成本模型没错，错在**"帧外增量是小区块"这个前提**。这颗板子上
帧外增量要么不存在，要么是全屏。

## 5. 留下的东西

- `services/myvendor_epic_blit.c`：整幅旋转改走 `epic_result()` —— HAL 的
  `EPIC_WaitDone()` 超时只加计数、仍返回 `HAL_OK`，之前会被当成功（屏上可能停在
  半张旧图）。这是**独立于本方案的真缺陷**，保留。
- 删掉 `lv_draw_sifli_epic_img.c` 的 `[epicimg]` 探针（WP-6 要求"提交前删"）。
- `docs/map/perf/verify/area_diff.c`：宿主穷举（HAL 的 Q15 查表 + 插值 + 幅值截断
  + 零角度旁路，逐像素核对"源行区间够不够"）。结论：0 px 外扩差 1 行，2 px 足够。
  以后若再做任何 clip 化的 EPIC 原语，这个工具可以直接复用。

## 6. 若要重新考虑，前置条件是什么

按顺序：

1. **先让帧外增量变小**：轨迹改成"只画尾巴 + 自己的擦除记账"（当前 `stamp_overlays`
   每 500 ms 重描整条），或让 rebase 的瓦片边条分别记账而不是并成整画布。
2. 再谈子矩形：那时 `[vrot] area` 才可能 >0；用 §5 的 `area_diff.c` 做寻址核对。
3. 余量问题（`T`）与脏区无关：只能靠更大的 R（PSRAM）或条带旋转，WP-11 已否决后者。

  —— 本次为临时探针，随回退一起删除；重做时照抄这两条即可。
- 负载：`bicycle_nsh demo start linear`、`bicycle_nsh gnss sim <gpx> fwd 45`。
- 判据：`[vrot] area n>0` 且 `avg ≤15 ms`；`[vrot] bakes` 次数下降；`ps` 的
  `bicycle_ui` 下降、`IDLE` 上升。
