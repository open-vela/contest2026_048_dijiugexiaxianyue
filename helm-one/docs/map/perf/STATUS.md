# 性能现状与已否方向（2026-10-28 收口）

一句话：**地图渲染这条线到顶了；后续只做视觉/交互层面的优化，不再做 CPU 优化。**

## 当前口径（40 km/h 演示负载，`BICYCLE_DEMO_LINEAR_KPH=40`）

固件 `build_date 202610282334`。航向朝上 3×90 s / 正北 2×90 s 窗口：

| 指标 | 航向朝上 | 正北 |
|---|---|---|
| 整幅重烘 | 0.10/s × 140 ms = **12~16 ms/s** | 0 |
| 合成（每次跟车重绘） | 4.9 fps × 12 ms = **59 ms/s 墙钟** | 5.2 × 11 ms = 57 ms/s |
| rebase 帧 | 3~4 帧/90 s ≈ 6 ms/s | 1~2 帧/90 s |
| 冷瓦片（`warms`） | 0~0.3 /帧（稳态） | 0~1 /帧 |

结论：**旋转只占约 1.5% CPU；地图侧最大项是"每 1 px 平移一次整视口重绘"的合成。**
完整数据：`docs/agent/evidence/WP-20/R1/MEASURE-40KPH.md`。

## 今天被数据否掉的两条（别再重做）

1. **子矩形旋转（只转脏区）**：7 轮 Codex ACCEPT、宿主穷举也过，但四组负载
   （demo/GPX 45/GPX 8/导航）`[vrot] area` **零命中** —— 帧外失效要么是全屏
   （rebase 瓦片边条合并、导航 stamp 重描整条路线+轨迹），要么不存在。
   详见 `docs/map/perf/ROT_AREA.md`。
2. **加大 R 余量（24→40）**：等窗口 + 归因 A/B 后是**持平**（120 km/h 44→35 ms/s，
   45 km/h 16→15 ms/s，事件数 5~19/窗，差异 ~1σ），不值得多付 37 KB PSRAM 与
   每次 +34 ms 停顿。`vmap_config.h` 的注释已写明，含"别引用旧的 +46% 误判"。

## 明确不做的

- **平移量化 1→2 px**：能省约 3% 墙钟，但地图 2 px 一跳 —— 用户 2026-10-28 明确否掉（降观感）。
- 后续若继续，方向是**视觉/交互**，不是 CPU。

## 还开着的（是"没测"，不是"已证明没有"）

- UI 任务除地图外的占用：`ps` 的 CPU 列（`CONFIG_SCHED_CPULOAD_EXTCLK`，采样窗约 2~4 s）
  显示 `bicycle_ui` 在 60% 量级，但**两列百分比哪一列是 CPU 尚未证实**，而地图侧各项
  加起来只有 7~8%。要关掉这个未知，成本是 20 分钟：主界面/数据页/菜单页各取一次 `ps`
  对照。**这是投入决定，不是技术空白。**
