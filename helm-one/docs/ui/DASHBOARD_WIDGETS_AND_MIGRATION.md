# 主界面格子：控件目录、画法与现有页面迁移

> 配套文档：[`MAIN_DASHBOARD_LAYOUT.md`](MAIN_DASHBOARD_LAYOUT.md)（8 格布局的
> 存储/BLE/线程模型）。本文解决两件事：
>
> 1. **格子里能放什么**——控件目录、每个控件在 1/2/4 格里的具体画法；
> 2. **现有页面怎么靠过来**——P01/P02/P03/P04/P05/状态栏/横幅逐项映射，
>    哪些能进格子、哪些必须保持专用组合。
>
> 所有尺寸/字号/颜色都按当前源码实测值（2026-11-02）反推，不是拍脑袋。

---

## 0. 三层模型（先记住这张图）

```
Surface（页面/区域）        HOME_CARD / RIDE_DATA / RIDE_DASH / MAP_STRIP / RIDE_DIAL
   │  定义像素几何：cols/rows/列宽权重/gap/pad
   ▼
Grid（格子）                2×4、2×5、2×4(列宽 124/98)、2×3 …
   │  布局文档只存 (col,row,w,h)
   ▼
Widget（控件）              CLOCK / VALUE / STATUS / ACTION / BAR / SPARK / PROFILE / …
   │  每种控件自己决定 1/2/4 格怎么排
   ▼
Metric（指标）              SPEED / TIME / DIST / HR / CAD / POWER / …
```

**关键原则：控件按“格”放，指标按“ID”取；页面只决定格子多大，不决定长什么样。**
这样 P03 的十项、P01 的时钟、P05 的四行，用的都是同一套 VALUE 画法。

## 1. 设计语法（Cell Grammar）

### 1.1 格子内部结构

```
┌──────────────────────────────────────────────┐
│▌  标签（ui_12 MUTE）        128  unit       │
│  ↑                ↑          ↑              │
│  3px 身份色条     左对齐      右对齐（定宽盒） │
└──────────────────────────────────────────────┘
```

统一规则（所有 surface 一致）：

| 元素 | 规格 | 说明 |
|---|---|---|
| 色条 | 3px 宽；1 格高 18、2 格高 40 | 颜色 = 指标身份色，不是告警色 |
| 色条间隙 | 4px（1 格）/ 6px（2 格以上） | 和现有 `helm_cell_make` / `helm_dash_row` 一致 |
| 标签 | `helm_ui_12`，MUTE；2 格以上可用 `helm_ui_15` | 1 格用短标签（「最大心率」→「最大」） |
| 数值 | num_28 / num_40 / num_56，INK | 字号由格子尺寸算，不由 App 选 |
| 单位 | `helm_ui_12`，MUTE，紧贴数值右侧 | 1 格默认不显示单位（放不下） |
| 次要行 | `helm_ui_12`，MUTE | 均值/极值/日期/「上次 …」 |
| 数值盒 | **定宽 + 右对齐** | 防止 `9`→`10` 时整行左右晃 |
| 单元格底 | 透明 | 底色由卡片提供；只有告警才铺淡红 |
| 圆角 | 0 | 圆角只在外层卡片 |

### 1.2 排版模板

| 模板 | 适用跨度 | 布局 |
|---|---|---|
| `ONE_LINE` | 1×1、2×1 | 色条 + 标签（左） + 数值+单位（右，同一基线） |
| `STACKED` | 1×2、2×2（窄值） | 色条 + 标签（上） + 数值+单位（下） |
| `HERO_BIG` | 2×2（无次要行） | 色条 + 标签（左） + num_56 大值（右，同一行） |
| `HERO_DETAIL` | 2×2（有次要行） | 色条 + 标签（左） + num_28 值 + 次要行（右侧上下两行） |

> **2×2 不能「num_56 + 标签在上 + 次要行」三者都要**：62px 高装不下
> 15（标签）+ 61（num_56）+ 15（次要行）= 91。所以要么标签在左、值用
> num_56、无次要行；要么标签在左、值降 num_28（30）+ 次要行 15 = 45 ✓。

选择规则（设备自动，App 复算）：

```
1. 若请求次要行：值盒高 = rect.h - 15；否则 rect.h
2. 若 num_56 的 max_chars 宽度 ≤ 值盒宽 且 61 ≤ 值盒高 → HERO_BIG
3. 否则若标签+数值能并排（标签宽 + max_chars*字宽 ≤ 可用宽）→ ONE_LINE
4. 否则 → STACKED
5. 都放不下 → 该跨度非法（编辑器标红）
```

字宽（实测）：`num_28 ≈ 16.75`、`num_40 ≈ 22.2`、`num_56 ≈ 29` px/字符；
行高：28→30、40→57、56→61；`ui_12` 行高 15、`ui_15` 行高 17。

### 1.3 宽度公式（编辑器和设备共用）

```c
/* rect = 格子像素矩形；p = 模板（ONE_LINE/STACKED/HERO_BIG/HERO_DETAIL） */
可用宽 = rect.w - 色条3 - 隙
         - (标签在左 ? 标签宽 + 隙 : 0)
可用高 = rect.h
         - (标签在上 ? 15 : 0)
         - (有次要行 ? 15 : 0)
font = 最大 f ∈ {56,40,28}：
         line_height(f) ≤ 可用高 &&
         max_chars(metric) * char_w(f) ≤ 可用宽
if (font == none) → 放不下
```

例：

| 场景 | 格子 | 可用宽 | 可用高 | 结果 |
|---|---|---|---|---|
| HOME_CARD 1×1，心率（3 字符） | 103×30 | 103−3−4−24−4 = 68 | 30 | num_28：3×16.75=50 ✓ |
| HOME_CARD 1×1，时间（5 字符） | 103×30 | 68 | 30 | num_28：5×16.75=84 ✗ ⇒ 非法 |
| HOME_CARD 2×1，时间（5 字符） | 208×30 | 208−3−4−24−4 = 173 | 30 | num_28：84 ✓ |
| RIDE_DATA 1×1，时间（STACKED） | 113×50 | 113−3−6 = 104 | 35 | num_28：84 ✓ |
| HOME_CARD 2×2，里程（4 字符 HERO） | 208×62 | 208−3−6−24−6 = 169 | 62 | num_56：4×29=116 ✓ |

> 这条公式解释了为什么「同一个指标在 P03 的 1 格能放、在主界面 1 格放不下」：
> 不是指标变了，是格子从 113×50 变成了 103×30。编辑器和设备必须用同一份
> `max_chars` / 字宽表算，否则预览和上板会差一格。

### 1.4 颜色与状态

| 状态 | 画法 |
|---|---|
| 有效 | 数值 INK；色条 = 指标身份色 |
| 无效（传感器未连） | 数值 `--` + MUTE；色条保持但降为 MUTE |
| 告警（HR≥150 / PWR≥250 / 车速≥30） | 整格淡红底 `HELM_COLOR_HR` + `LV_OPA_30`；数值仍 INK |
| 暂停/未记录 | 数值照常，右上角由状态栏的 REC 表示；单元格不额外变灰 |
| 夜间主题 | 只用 palette token；不写死颜色 |
| 选中/焦点 | 单元格不参与菜单焦点，不画高亮 |

**颜色只承载形状**：色条、色带、填充、整格淡底。正文永远 INK/MUTE；
只有 num_56 的英雄数字允许用身份色（大字号对比度 ≥3:1）。

### 1.5 溢出与格式化

- `max_chars` 是硬约束；格式化函数按现有 `helm_fmt_*` 规则：
  - 速度/里程：`%d.%d`，≥100 km 只留整数；
  - 时间：`MM:SS`，≥100 分钟转 `HH:MM`；
  - 心率/踏频/功率/爬升：整数；
  - 坡度：带符号 1 位小数。
- 放不下时**不缩字号、不换行**：编辑器拒绝；设备端兜底显示 `--`（不会把
  数字截成半截）。
- 不在 tick 里测文本宽度：所有盒宽在 build 时算死。

### 2.2 `CLOCK`（0x01）

| 跨度 | 画法 |
|---|---|
| 1×1 | `22:12` num_28 居中；无日期 |
| 2×1 | `22:12` num_28 左 + `11月1日 周日` ui_12 右 |
| 1×2 | `22:12` num_28 上 + 日期下一行 |
| 2×2 | `22:12` num_40 左 + 日期/星期两行右（垂直居中） |

```
2×1:
┌──────────────────────────────────────┐
│ 22:12                11月1日 周日    │
└──────────────────────────────────────┘
2×2:
┌──────────────────────────────────────┐
│                                      │
│  22:12        11月1日                │
│               周日                   │
│                                      │
└──────────────────────────────────────┘
```

- 颜色：时间 INK、日期 MUTE；无身份色条（不是指标）。
- 无效：`--:--` + `--`；时间同步失败时保持上一帧，不闪 `00:00`。
- 24h 固定；12h 是全局设置，v2。

### 2.3 `VALUE`（0x02）——最常用

四种跨度，四种密度：

```
1×1（103×30，ONE_LINE）
┌──────────────────────────────────────┐
│▌ 心率                        128    │
└──────────────────────────────────────┘

2×1（208×30，ONE_LINE）
┌──────────────────────────────────────┐
│▌ 平均心率                    128 bpm│
└──────────────────────────────────────┘

1×2（103×62，STACKED）
┌───────────────┐
│▌ 心率         │
│               │
│  128 bpm      │
│  均 118       │
└───────────────┘

2×2（208×62，HERO_BIG）
┌──────────────────────────────────────┐
│▌ 里程              123.4 km          │
│                                      │
└──────────────────────────────────────┘

2×2（208×62，HERO_DETAIL，带次要行）
┌──────────────────────────────────────┐
│▌ 里程        123.4 km                │
│              均速 18.2               │
└──────────────────────────────────────┘
```

规则：

- 1×1/2×1：标签在左、数值右对齐；1×1 默认隐藏单位。
- 1×2/2×2：标签在上（或左），数值 num_28/56；2×2 优先 HERO。
- `flags`：bit0 显示单位、bit1 显示标签、bit2 显示次要行（指标自带时）。
- 无效值：`--` + MUTE；不隐藏整格（隐藏会让布局跳动）。
- 告警：整格淡红（HR/PWR/SPEED 三项阈值见 §1.4）。

### 2.4 `DUAL`（0x03）

```
2×1:
┌──────────────────────────────────────┐
│▌ 心率  128        均 118     峰 172  │
└──────────────────────────────────────┘
2×2:
┌──────────────────────────────────────┐
│▌ 心率                                │
│  128 bpm        均 118 · 峰 172      │
└──────────────────────────────────────┘
```

- 主指标用标准 VALUE 画法；次指标用 ui_12 MUTE，跟在主值右侧或下一行。
- 典型组合：心率+均心率、心率+最大心率、速度+均速、里程+时间。
- 次指标的 `max_chars` 也要校验；放不下就把次指标移到第二行（2×2）。

### 2.5 `STATUS`（0x04）

```
1×2（103×62，现状三行）
┌───────────────┐
│ ◉ 9 颗卫星    │
│ ● 已定位      │
│ ● 上次 12.3km │
└───────────────┘

2×1（208×30，横排；用短标签）
┌──────────────────────────────────────┐
│ ◉ 9 星    ● 定位    ● 上次 12.3     │
└──────────────────────────────────────┘
```

- 图标槽固定 16×16，文字从同一竖线起（现有实现已修过这个对齐问题）。
- 2×1 横排必须用短标签（`9 星`/`定位`/`上次 12.3`），否则 208px 放不下
  三组完整文案。
- 卫星图标：有星绿、无星红；定位点：实心=已定位、空心=未定位；上次里程 MUTE。
- 1×1：只显示第一行（卫星数）；其余两行通过 `flags` 轮换（每 3 s）或隐藏。
- 三行都无效时整块显示 `--`，不空着。

### 2.6 `ACTION`（0x05）

```
1×1（103×30）：
┌───────────────────────────────┐
│      [ 开始骑行 ]             │  // 只留动作字，无键帽、无环
└───────────────────────────────┘

2×1（208×30，现状）：
┌──────────────────────────────────────┐
│ [长按按键] 开始骑行            (▼)   │
└──────────────────────────────────────┘
```

- 状态文案：待机「长按按键 · 开始骑行」、记录中「暂停」、暂停中「继续」。
- 2×1/2×2 才有提示环（22px，±4px 浮动，只在有交互时动）。
- 1×1 用短文案「开始骑行」（4 字 60px + pad 28 = 88 ≤ 103）。
- 不响应触摸/点击（实体键操作），只是提示；点击可留空。

### 2.7 `MULTI`（0x06）——紧凑多项条

```
2×1（208×30，n=4，P02 四格）
┌─────────┬─────────┬─────────┬─────────┐
│ 里程 km │ 时间    │ 踏频 rpm│ 海拔 m  │
│ 12.3    │ 52:18   │ 84      │ 128     │
└─────────┴─────────┴─────────┴─────────┘
```

- n ∈ {3,4}；每格等宽；内部用 `VALUE_COMPACT`（标签 ui_12 + 值 ui_15）。
- **单位并进标签**（`里程 km`、`踏频 rpm`），值只留数字——这是 P02 现有
  60×30 盒的做法，也是 30px 高度下唯一放得下的做法。
- 行高账：标签 ui_12 行高 15 + 值 ui_15 行高 17 = 32 > 30；现有 P02 盒就是
  靠 0 padding + 基线压进去的，MULTI 沿用同一压法（值贴底、标签贴顶），
  不额外加 padding。
- 2×2 时可升级为标签 15 + num_28 30 = 45 ≤ 62，值可读性更好。
- 用于 P02 的四格条、P04 的三卡条；两者都保留各自的紧凑字号（P02 值 15px、
  P04 时间/里程 MiSans 22 + 速度 num_28），不强行统一到 num_28。
- **线格式**：v1 的 8B 记录只带一个 `metric`。MULTI 的有序多项需要 v2 的
  扩展记录（`type,n,metric[n]`，n≤4）或独立 config blob；v1 先不开放
  MULTI 的 App 配置（P02 四格固定），避免为它提前扩协议。

### 2.8 `BAR`（0x07）——数值 + 分区量条

```
2×2（208×62）
┌──────────────────────────────────────┐
│▌ 速度                     24.5 km/h  │
│  [=========|          ]              │
│   0          30          60          │
└──────────────────────────────────────┘
```

- 上层 14px 填充（按经过的分区取深色）+ 下沿 4px 分区底尺 + 2px 墨色前沿。
- 刻度在带上方（10px 滑块会压住带内文字——P02 已有结论）。
- 分区表：速度 0/18/32、心率 120/150、功率 FTP 百分比（v2）。
- 无效：空填充 + `--`；不画前沿。
- 最小高度：2×1 在 RIDE_DATA（228×50）可放；HOME_CARD 只能用 2×2。

### 2.9 `SPARK`（0x08）——数值 + 走势

```
2×1（228×50，RIDE_DATA）
┌──────────────────────────────────────┐
│▌ 心率 128        ╱╲    ╱╲___         │
│                  ╱  ╲__╱     ╲___    │
└──────────────────────────────────────┘
```

- 30 点、1 s/点、30 s 窗口（现有 `helm_spark` 同参）。
- 面积填充：最上沿 `HELM_CLIMB_FILL_TOP_OPA=110`，向下线性淡出；2px 折线。
- 无数轴、无网格；底槽可选 1px HAIR。
- 只给有独立历史序列的指标（速度/心率/功率/踏频/海拔）；时间/里程不出图。
- 无效：走势区留空，不画 0 线。

### 2.10 `PROFILE`（0x09）——海拔剖面

```
2×1（228×30）
┌──────────────────────────────────────┐
│ ▁▂▃▅▆▅▃▂▁▂▃▅▆  [前方 6 km]          │
└──────────────────────────────────────┘
2×2（228×62）加高，标注最低/最高
```

- 已骑段整条灰（`HELM_COLOR_ELEV_DONE`）；未骑段按坡度绿/黄/红；
  交界 = 2px 墨色前沿；当前位置倒三角 15×10。
- 记录模式：最近 10 分钟（60 点 × 10 s）；导航模式：前方 6 km 窗口。
- 无数据：一行「无海拔数据」/「正在记录海拔…」，不画空坐标轴。

### 2.11 `ARC`（0x0A）——270° 时速弧（P02 专用）

```
2×4（228×258 页面，最小 152×152）
┌──────────────────────────────────────┐
│            ╭─────────╮               │
│          ╱             ╲             │
│         │    28.6       │            │
│         │    km/h       │            │
│          ╲             ╱             │
│            ╰─────────╯               │
└──────────────────────────────────────┘
```

- 152×152、7px 弧、270°、7 根刻度；颜色按速度区间（绿/黄/橙）。
- 中心英雄值 num_56 + 单位。
- **这是页面级控件**：HOME_CARD 的 2×2 只有 208×62，装不下；只有
  整页 surface（2×4 或更高）能放。所以 P02 不强行网格化。

### 2.12 `HERO`（0x0B）——P05 左卡

```
1×4（124×258）
┌──────────────┐
│    28.6      │  num_56，NAV 橙
│    km/h      │
│  [====    ]  │  5px 量条 0~60
│              │
│  🕐 时间     │
│  52:18       │  num_32
│  ─────────   │
│  ▌爬升 128 m │
│  ▌坡度 2.1 % │
└──────────────┘
```

- 速度、量条、时间、两个小结项都是可配置字段（speed/time/sub1/sub2）。
- 最小 124×120；RIDE_DASH 的 1×4 正好。
- 内部保留现有 P05 的排版，不拆成 4 个独立 VALUE（拆了会丢掉“左栏锁死”的
  扫读优势）。

### 2.13 `NAV`（0x0C）与 `TEXT`（0x0D）

- `NAV`：2×1 紧凑（徽章 + 距离 + 动作）、2×2 完整（+ 目的地/剩余）。
  当前通栏横幅仍走系统 chrome，不放进网格；`NAV` 是给数据页预留的。
- `TEXT`：2×1 段落标题（ui_15/22 + 可选 3px 橙色下划线），用于 P03 的
  「骑行数据」这类页头；v1 页头仍由 `helm_speed_head` 承担。

## 3. Surface 目录（页面/区域）

| ID | Surface | 页面 | 像素区域 | 网格 | 格大小 | 开放控件 |
|---|---|---|---|---|---|---|
| 0 | `HOME_CARD` | P01 主界面卡 | 208×126 | 2×4 | 103×30 | CLOCK/VALUE/STATUS/ACTION（v1）；+DUAL/MULTI（v2） |
| 1 | `RIDE_DATA` | P03 全数字页 | 228×258 | 2×5 | 113×50 | VALUE/DUAL/SPARK/TEXT |
| 2 | `RIDE_DASH` | P05 X1 仪表台 | 228×258 | 2×4，列宽 124/98 | 124×64 / 98×64 | HERO（仅左列 1×4）+ VALUE/SPARK（右列 1×1） |
| 3 | `MAP_STRIP` | P04 地图页底部 | 240×80 | **固定 3 项** | 77×72 | `MULTI(3)`（不开放自由网格） |
| 4 | `RIDE_DIAL` | P02 表盘页 | 240×296 | **非网格**（固定组合） | — | 4 格 MULTI + PROFILE 可配置，弧/带固定 |
| 5 | `CLIMB` | 海拔页（可选） | 228×258 | 2×3 + 剖面 | 113×47 | PROFILE + VALUE |

> `HOME_CARD` / `RIDE_DATA` / `RIDE_DASH` / `CLIMB` 是**网格型** surface，
> 走布局 blob（格坐标）；`MAP_STRIP` / `RIDE_DIAL` 是**固定组合** surface，
> 只存“选哪几项”的 config，不存格坐标。两者不要混用同一份布局文档。

### 3.1 为什么 P02 不做自由网格

- 270° 弧最小 152×152：HOME_CARD 的 2×2 只有 208×62；RIDE_DATA 的 2×2 是
  228×102，高仍小于 152；只有整页 2×4（228×258）能放，但放完弧就没地方放
  速度带/心率带/四格/剖面。
- 弧 + 两条分区带 + 剖面是**层叠组合**，拆成格子会破坏“左眼看弧、下眼看带”
  的扫读顺序。
- 结论：P02 保留固定组合，只把**四格**和**剖面**换成目录里的 `MULTI` /
  `PROFILE`，并让 App 配置这两块的数据项；弧/带不开放布局编辑。

### 3.2 RIDE_DASH 的列宽权重

P05 的左栏 124、右栏 98 是从 `num_56 "28.6" = 116px` 反推的，不能等分。
surface 描述里带 `col_w[] = {124, 98}`；布局文档仍只存格坐标，像素由设备算。
App 的预览读同一份 surface 描述（随目录 JSON 导出）。

### 3.3 HOME_CARD 的 8 格组合示例

| 组合 | 占格 | 说明 |
|---|---|---|
| CLOCK 2×1 + STATUS 1×2 + HR 1×1 + DIST 1×1 + ACTION 2×1 | 8 | **默认**；信息最全 |
| CLOCK 2×2 + HR 1×1 + DIST 1×1 + ACTION 2×1 | 8 | 大时钟；没有 STATUS |
| CLOCK 2×1 + HR/CAD/PWR/GAIN 各 1×1 + ACTION 2×1 | 8 | 数据向；没有 STATUS |
| CLOCK 2×2 + ACTION 2×1 + HR 1×1 + DIST 1×1 | 8 | 最保守的“大时钟 + 一键 + 两数” |
| 8 × VALUE 1×1 | 8 | 纯数据墙；无时钟/CTA |

> 4 格的 `VALUE` 是 2×2（208×62），可以放 num_56 英雄值；但 8 格全用 1 格时
> 每格只有 103×30，只适合短标签 + ≤4 位数字。

- 取数统一走 `bicycle_runtime_t`（现有 `helm_fill_all` / `helm_fill_group`

`tools/gen_dash_catalog.py` 从 C 表导出，App 侧不手抄。

## 6. 迁移顺序（每步都能单独验收）

| 步骤 | 内容 | 验收 |
|---|---|---|
| M0 | 抽出 `helm_cell`：色条/标签/数值/单位/状态，供 P03 与 P05 共用 | P03 视觉等价：字号/对齐不变，格宽 +13px |
| M1 | P03 → `RIDE_DATA` surface（2×5，10×VALUE） | 默认布局视觉等价；任意 2 格合并正常 |
| M2 | P01 → `HOME_CARD`（默认布局：CLOCK/STATUS/2×VALUE/ACTION） | 信息集合一致；1/2/4 格各一张模拟器图 |
| M3 | P05 → `RIDE_DASH`（HERO + 4×VALUE，列宽 124/98） | 左右栏宽度/字号不变；功率无效显示 `--` |
| M4 | P04 → `MULTI(3)`（固定三槽） | 三卡宽度/字号不变；三项可选 |
| M5 | P02 → `MULTI(4)` + `PROFILE`（弧/带不动） | 四格/剖面与现状一致；弧不变 |
| M6 | App 编辑器：先 HOME_CARD，再 RIDE_DATA | 手机改布局 1 s 内生效；非法布局被拒 |

**先做 M0/M1 的原因**：P03 本来就是 2×5 网格，改造成本最低，且能验证
“同一套 cell 画法在 113×50 与 103×30 两种密度下都不失控”。M0 完成后，
P01/P05/P04 都只是换 surface 参数。

## 7. 反模式（明确不做）

1. **不把 ARC 塞进 2×2**：152×152 放不进 208×62，强行缩会失去表盘的扫读优势。
2. **不让 App 选字号/颜色**：只给指标 ID 和跨度；字号由 §1.3 算，颜色由目录定。
3. **不在布局里存标签/单位**：只存 ID，否则中英文/英制切换会失效。
4. **不允许 1 格放 5 个字符**：`时间`（`52:18`）在 HOME_CARD 必须 2 格；
   `里程` 是 4 字符，1 格可以。编辑器直接标红，不靠固件截断。
5. **不做自动流式补位**：空格保留空位，用户自己拖；自动补位会让布局在
   数据变化时跳动。
6. **不因为传感器无效折叠整行**：显示 `--`，保持网格稳定。
7. **不在 tick 里做布局/测宽**：所有几何在 build 时算死，tick 只改文本。
8. **不把状态栏/导航横幅做成格子**：它们是 chrome，随状态出现/消失。

## 8. 一页纸总结

- **控件**：CLOCK、VALUE、STATUS、ACTION 是 v1 的四个基础件；DUAL、MULTI、
  BAR、SPARK、PROFILE、ARC、HERO、NAV、TEXT 是 v2 的组合件。
- **画法**：1 格 = 一行“色条+短标签+num_28”；2 格 = 全宽一行或半宽两行；
  4 格 = 2×2：无次要行时 num_56 英雄值，有次要行时 num_28 + 次要行；
  字号/模板由格子尺寸自动选。
- **迁移**：P03 先做（本来就是网格），P01 次之（信息集合不变），P05 保留
  124/98 列宽，P04 变 `MULTI(3)`，P02 只把四格/剖面接进目录、弧和带不动。
- **不变的**：指标 ID、cell grammar、颜色规则、字号阶梯。变的只是 cell 的
  像素大小和摆放位置。
